# Lessons learned (B737 v2) — read before writing or changing pipeline code

Rule (2026-10-04): every problem found is recorded here immediately. Newest at the bottom.

## CFD / numerics
1. CPU density-based runs have slow modes in the tail/aft fuselage (tau ~550-600 it at CFL 10; wing ~250 it). CM can move 0.09 over a run. Decide "settled" from the extrapolated remaining change (CL 5e-4, CD 0.5 count, CM 1e-3), never from a fixed per-100-iteration drift. (research/drift_analysis.md)
2. Never use an unsettled point in the alpha secant: it produced a negative slope and a wrong-direction step (C5, 3.554 -> 3.43 deg, ~2 h lost).
3. C5 sits at a transonic lift break: lift slope 0.035-0.09 per deg, wing dCD/dCL 0.15-0.26. Slope guards must accept 0.02-0.20 per deg.
4. First alpha step uses an assumed slope (0.1 per deg), not a blind +1 deg.
5. The far-field face-value mass imbalance has a floor (~0.0043): report it, never stop on it (C5 run 1 stalled 1,892 iterations).
6. Runs saved only at the end lose their field on an alpha step or abort: autosave every 500 iterations.
7. GPU: hybrid initialisation with a pressure far-field can give unphysical velocities (Ansys GPU limitation) -> standard init or init from CPU data.
8. The GPU solver audit must fail closed (missing transcript = fail), use the final transcript and confirm the native GPU solver is active.
9. Shock position = largest positive Cp gradient (pressure recovery) aft of the suction peak.
10. Compare runs only at the same alpha (T5 uses --fixed-alpha).
11. Searches need alpha bounds (-2..16 deg), a 1 deg step cap and a stall branch (C3 near CLmax: report the best settled point as cl_unreachable).

## Process / tooling
12. Chain tasks with deps in one queue.
13. Queue-runner runs from a Bash background task (not hidden Start-Process: sandbox exec then fails with 0xC0000142); one task per launch under the 2 h cap.
14. Audits write findings incrementally, in process order, with a time budget.
15. Rerun tests before every commit.
16. A failed step must never hold the Fluent licence: per-step timeouts and killing exactly the recorded project pids.
17. Post-processing launched in the background must be checked for completion (exit code + post_report.json), not assumed.
18. Seed every alpha0 from flow5 (or C5 CFD + flow5 delta) and log its basis; C5 run 1 used an unrecorded hand guess of 2.5 deg vs flow5 3.80 deg (CFD answer ~3.6 deg) and lost a cold run.
19. Reference values must come from the verified geometry report (P3 MAC 3.4716 m), not hand constants (conditions.py used 3.403 m -> CM 2% off).
20. Save pressure and viscous force components and measured y+/prism coverage in every run's post step; the plan requires them and absence of mesher warnings is not coverage evidence.
21. flow5 lift is inviscid, incompressible and wing-alone (viscous = drag only); never use flow5 alphas raw as CFD seeds, only as same-planform deltas plus per-aerofoil compressible/viscous corrections.
22. Dump the full solver settings (gradient, flux, turbulence options, materials, wall thermal) for every CPU and GPU run so equivalence is evidence, not assumption.
23. Reuse of a finished run must verify mesh, alpha, solver, precision and policy version, never status alone.
24. Each A/B test needs its own adoption criterion; never reuse another gate's tolerances.
25. Mesh acceptance must enforce the documented quality floor or record an explicit waiver (g650 OQ 0.018 < 0.02).
26. Section force integration must close the contour including the blunt trailing-edge face.
27. Field mapping between meshes/exports must validate every face (distance, uniqueness), not a median.
28. Result summaries must tag each run's role and pick the authoritative route; never glob all result.json files.
29. The transient on the steady half-model mesh is a visualisation, not a resolved SRS result; say so in every report and never quote statistics from it.
30. Compare wings only at a common CL: correct each result to the target CL with its local dCD/dCL.
31. Every geometry variant must be traced through mesh and solve paths by a test; the trimmed domain was written but never read.
32. Swept-wing 2D analysis must convert Mach, cl, alpha and t/c to the sweep-normal plane together; P10SEED converted only Mach (caught on review).
33. A clean script exit does not mean Fluent exited: check for and kill the run's own leftover processes after close, or the next solver run cannot get the Student licence.
34. Before any transonic CFD campaign, run a section-level sanity check (spanwise cl from flow5 + Korn M_dd per section at the sweep-normal Mach) and compare twist/washout with the real aircraft; C5's overloaded no-washout tip and strong shocks were visible from v1 (CD 0.0469) and the basis note 'no washout' but were not flagged.
35. 2D compressible XFoil (Karman-Tsien) is invalid once sections are supersonic; check CFD Cp against Cp* before spending effort on compressible polars.
36. A slope fed to the alpha search must match the search variable (total-aircraft CL), not a component (wing-only) slope; never scale a transonic cruise slope to take-off.

- (2026-10-05) Offline field comparison without a licence: Fluent .dat.h5 holds face fields in mesh face order (results/1/phase-1/faces/SV_*/1; CPU stores boundary faces only, the GPU solver all faces in float32) and cells/SV_*; mesh in the .cas.h5 (meshes/1/...). SV_WALL_SHEAR there is the shear FORCE per face (N), and its sign is opposite between the CPU and GPU solvers. Use this route for CPU/GPU or grid comparisons while the licence is busy.
- (2026-10-05) The native GPU solver silently turns warped-face gradient correction OFF (unsupported; transcript 'GPU solver defaults are activated') and stores different gradient/symmetry-gradient flags: on a polyhedral mesh a GPU-vs-CPU comparison is never 'same numerics'. At a transonic lift break (strong shocks M 1.4-1.6, wing slope ~0.05/deg) scheme differences move the shock-induced separation and give ~10 % CL: treat CL there as scheme-sensitive and test uniqueness by swapped warm starts.
- (2026-10-05) Plan step T5 reads gpu_T2/final.dat.h5 and --seed-from gpu_T2 (result.json); a GPU run killed before its final write leaves only autosave files, so T5 can never run. Warm-start steps should accept the newest autosave (with case) or fail with that reason at plan time.
- (2026-10-05) Geometry vs real 737-200 (research/geometry_discrepancies_737.md): C5 CFD 479 counts vs real ~320-335 (Krull regression of Boeing polar data, Sref 91.04) vs xlsx 432 -> the xlsx target is itself ~100 counts above the real aircraft; never call it "the real 737". Biggest model errors: no washout (build_foils.py normalise() derotated ~1 deg of incidence embedded in the UIUC sections), outboard overload (c*cl 1.1-1.5x elliptic at eta 0.72-0.96), missing yehudi (root chord 4.79 vs 7.32 m), undersized blunt inlet (0.91 vs 1.37 m), no belly fairing. Under-predicted friction (wall functions) hides ~55 counts of the pressure-drag excess.
- (2026-10-05) Normalising/derotating source airfoil coordinates silently deletes design twist: when importing measured sections, record the chord-line incidence first and carry it into the twist definition.
- (2026-10-05) Curvature sign-change counts on coarse (23-pt) coordinates depend on the parser/derivative method; the initial count (13-17 changes, "wavy") was an artefact. Check by plotting curvature of each surface separately before claiming waviness.
- (2026-10-05) Courant 20 (ramp 300:10 -> 20) is result-neutral on C5 g400 (|dCL| 1e-4, |dCD| 0.02 counts) and cuts iterations 42 %: use it for later CPU density-based runs once the plan adopts it; do not hot-edit the plan of a running chain.
- (2026-10-05) chain.py loads the plan once at start: plan edits never reach a running chain. Change settings by a resume plan of the remaining steps, handed over at a step boundary; restarting the full plan would re-run unfinished early steps (e.g. T2 GPU). The Courant ramp in run_case restarts at every alpha step (local iterations), so keep its low-CFL start short.
- (2026-10-05) Background watchers launched without an explicit timeout die at the 30-min default: always pass timeout 7200000 (the watcher script itself exits at 115 min).
- (2026-10-05) post_g400 wrote all products at 03:35 but its process never exited; the chain's 2 h post bound killed it at 05:35 and recorded done (post_report present). Non-blocking (posts run in parallel), but every post will hold a process for 2 h: find what keeps case_post alive (check post_g650) before the transient/report phase.
- (2026-10-05) Review caught that an exhausted secant search whose CL-settled state already met final_minimum skipped the all-coefficient final settle (would report CL-only convergence). Any relaxed intermediate rule needs the final step to re-check under the strict rule unconditionally. Give test runs a fresh --basetemp under TEMP.
- (2026-10-05) C2 creep diagnosis: wing CL/CM frozen from ~850 it; the whole late creep is the htail (CL 0.0064->0.0015, CM -0.031->-0.010 over 650-1850 it) and aft fuselage (CM +0.018->+0.032). Slow, monotone (not oscillating) evolution of the tail-root/aft-body separation and wing-wake/downwash at the tail; CORRECTION: Fluent density-based already uses Weiss-Smith low-Mach preconditioning, so the cause is the slow physical relaxation of the tail-root/aft-body separation and wake/downwash transport (plus CFL-limited stretched BL cells), not missing preconditioning. Normal for full-configuration transonic RANS (DPW-IV: corner-flow/junction separation dominates CM); it governs settle time and CM uncertainty. Monitor htail+fuselage components when judging convergence.
- (2026-10-05 11:45) CORRECTION to the post_g400 'never exited' lesson: C2 post wrote all products within seconds of the run (11:02) and no post process remains, yet chain_log shows no done row. The 7200 s on post_g400 is most likely the chain's deferred bookkeeping of parallel posts (logged at its next check/bound), not a hung process. Verify from the post folder timestamps, not chain_log elapsed.
- (2026-10-05) C1 lost its converged result: after the settle passed (6,500 it, alpha 5.187, CL 0.4878, CD 0.05936, CM -0.0219) export_walls raised a pyfluent field-info RuntimeError ('CDR: invalid argument ... not a pair'); the CPU export is unguarded and runs BEFORE save_final and result.json, so nothing final was written and the chain marked C1 failed. - (2026-10-05) Python read()/write() edits on Windows silently convert CRLF->LF: a one-line fix rewrote all 1,600 lines of run_case.py in git. Use open(..., newline='') for both read and write when editing files by script.

## 2026-10-06 URANS (GPU, C5) setup lessons
- Steady GPU case carries Courant 200 and T/rho relaxation 1.0 into transient; with 20 inner iterations the energy equation blew up (T clipped 5000 K, NaN at step 2). Set transient controls explicitly.
- The C5 case is density-based: the Courant setting is `solution.controls.courant_number`; `p_v_controls.flow_courant_number` is inactive (InactiveObjectError) and the guard silently logged not_set -> still diverged at step 15. Always read back `applied`/not_set before trusting a control change.
- Driver must stop on NaN/unphysical CL/CD (divergence guard) instead of stepping on a dead field.
- `file.export.ensight_gold` needs `cellzones=list(cell_zone_conditions.keys())`, `interior_zone_surfaces=[]`; otherwise "invalid cell thread id" and a GPU segfault. Write the .geo once and point later .encas files at it (189 MB saved per frame).
- Fluent solution-animation PNGs are useless headless (edge-on/grey); use the GUI for live view and EnSight + ParaView for the video.
- Correction: the C5 GPU case is pressure-based coupled (solver gpu-pb), not density-based. In GPU transient neither `controls.courant_number` nor `p_v_controls.flow_courant_number` is active.
- Fluent aborts a dual_time_iterate chunk on a floating point exception WITHOUT raising in pyfluent; the driver kept counting steps. Now a chunk that does not advance flow time is treated as divergence (test added).
- Energy residual spikes inside time step 1 (T clipped at 7308 cells after step 1) even with relaxation 0.8 -> the problem is the transient start itself, not only the controls.
- GPU probe (2026-10-06): from the steady C5 field, 1st-order time ran clean for 6 steps at dt 1e-4 (in 20), 2.5e-5 (in 20), 2.5e-4 (in 5), no clipping. The 2nd-order-bounded formulation was the trigger. Driver default is now --time-order 1.
- URANS T3 (2026-10-06, 1st order, dt 2.5e-4, inner 10): stable to step 20, then energy residual spikes (T clipped at 51 -> 10,831 cells), CL 0.54 -> 0.37 at step 22, FPE. Driver then hung waiting on Fluent (python + Fluent idle) -> killed. The idle hang explains the ~15 % GPU load.
- ROOT FACT: the Fluent GPU solver supports Coupled p-v only for STEADY; on switching to transient it silently replaces Coupled with SIMPLE ("GPU solver defaults ... flow scheme coupled -> simple"). That is why no Courant control exists in transient. Transonic compressible flow with SIMPLE needs low URFs (p 0.3, mom 0.5, density 0.5, energy ~0.7) and/or smaller dt. GPU solver is pressure-based only (no density-based).
- GPU load: Ansys recommends >= 2M cells per GPU; at 1M cells an RTX 5070 Laptop is not saturated. Task Manager '3D' does not show CUDA load; use nvidia-smi.
- GPU probe2 (2026-10-06): the transient blow-up starts in ~10-30 cells at x 11.37, y 5.05, z -0.29 m (under the wing at the pylon/nacelle junction); the rest of the field is normal (Tmax 254 K at t0). SIMPLEC + low URFs (p 0.3, mom 0.5, rho 0.5, T 0.7) delays it (CL steady 0.543-0.544 for 21 steps, hot cells flicker 300-2600 K) but still FPE at step 22. Next: mesh improve-quality on the run copy + max temperature limit 400 K.
- "CDR: invalid argument ... not a pair" from a report/compute call is what pyfluent returns AFTER a Fluent floating point exception; look for the FPE in the transcript first.
- GPU probe3 (2026-10-06) FIX: SIMPLEC + URFs (p 0.3, mom 0.5, rho 0.5, T 0.7, k/w 0.6) + max temperature 400 K: 60 steps x 20 inner clean, CL 0.544-0.547, CD 0.0510-0.0516. Cap active 21 times in 1200 inner iterations (median 2, max 17 cells) - local band-aid at the pylon/nacelle junction cells, no effect elsewhere (field 220-290 K). Mesh improve-quality changed nothing (min orthogonal quality 0.044, 0.1 % cells < 0.07). GPU load while computing: mean 37 %, p90 92 % (mean diluted by per-step Python field pulls). Driver now aborts if the scheme or cap is not applied. Launched URANS T4 (200 steps, dt 2.5e-4, inner 20, GUI).
- URANS T4 (2026-10-06, SIMPLEC + URFs + 400 K cap, dt 2.5e-4, inner 20): clean to step ~110 (CL 0.5466 -> 0.5535, CM -0.162 -> -0.174 slow drift), cap hits grew (27 -> 118 cells), then whole-field clip + FPE at step 120 (CL 1.06, CD -0.43). The cap only delays it.
- Hot-spot location: 1.5 cm off the PYLON leading edge (x 11.37, y 5.05, z -0.29), in the 0.27 m gap between the engine top (0.12 m below) and the wing lower surface (0.19 m above). Physical stagnation T is ~244 K at M 0.74, so anything above ~260 K there is numerical: poor cells at the pylon-LE / nacelle / wing junction. Fix belongs in the mesh (local sizing/quality at that junction), not in solver knobs.
- Divergence guard gap: CD < 0 was not caught (only |CL| > 3, CD > 1). Add CD < 0 and |dCL| per chunk checks.
- SBES mesh attempt 1 (2026-10-06): a Proximity sizing (3 cells/gap, min 0.01*scale) scoped to whole labels mainwing/engine/pylon/nacelle_duct resolves EVERY thin gap (wing thickness, duct annulus) -> 2.3M cells at scale 1.0, cap forced scale 2.9 (everything 3x coarser), min OQ 0.022. Rejected. Lesson: never scope proximity to whole large labels; refine a junction with a small fixed-size BOI box instead, and keep local sizes independent of the global scale.
- Pylon-junction cells in the prod mesh have OQ >= 0.10 (Improve Volume Mesh floor), so the GPU transient blow-up there is not a bad-OQ problem; more likely under-resolved transonic flow in the 0.27 m engine-pylon-wing channel. Local refinement targets resolution, not OQ.
- Technical review (2026-10-06) + Ansys v261 GPU limitations page: "using a steady-state solution to initialize a transient case does not work correctly when solving the energy equation"; fix = iterate steady in the SAME session, then switch to transient. All earlier GPU transients read steady data from file and switched immediately -> likely the root of the energy blow-ups. Driver now runs 100 steady iterations in-session first.
- Same review: keep SIMPLEC default URFs (2026 R1 uses p-URF in the compressible transient linearisation); pick dt from shock-cell CFL (wing cells ~0.09 m, u+a ~620 m/s -> dt ~1e-4..1.5e-4, not 2.5e-4), 10-15 inner; viscous heating ON for pressure-based; SST compressibility correction OFF; no Low-Diffusion-Central / Optimized LES numerics near shocks; reduce dt before adding inner iterations. Double precision on GeForce is FP64-throttled (test speed before adopting).
- SBES mesh attempt 2 (2026-10-06): a fixed 0.025 m BOI box (1.3 x 0.9 x 0.75 m) at the pylon junction adds ~0.9M cells (1.94M total at scale 0.96); 0.05 m adds ~60k, 0.08 m ~40k. Poly-hexcore cost rises steeply below ~0.05 m (my cube-count estimate was 10x too low). Fluent Meshing rejects a second BOI import: put several boxes in ONE boi .msh as separate wall zones (write_boxes helper).
- URANS T5 (2026-10-06): 100 steady GPU iterations in-session (clean, residuals flat ~1e-4) then transient SIMPLEC with DEFAULT URFs, dt 1e-4, no T cap: CL 0.54 -> 0.24 by step 7, whole-field clip, diverged. The in-session start alone does not cure it; Fluent default URFs are worse than the low profile. Next: T6 = same start + low URFs, no cap.
- URANS T6 (2026-10-06) STABLE RECIPE: 100 steady GPU iterations in-session, then transient SIMPLEC + low URF profile, 1st-order time, dt 1e-4, inner 15, no T cap: 300 steps (0.03 s) completed; 5000 K bound touched 9x (<= 7 cells) and recovered. CL drifts 0.542 -> 0.557, CM -0.154 -> -0.176 (transient moving off the steady GPU state). Junction mesh refinement dropped as unnecessary.
- SBES on GPU (settings API, Fluent 26.1): only after solver.time = transient: setup.models.viscous.hybrid_rans_les = "stress-blended-eddy-simulation" (allowed: none / stress-blended-eddy-simulation); then viscous.sbes.{hybrid_model, les_subgrid_scale_model, update_interval_k_omega} become active.
